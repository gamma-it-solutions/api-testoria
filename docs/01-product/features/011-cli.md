# Feature 011 — Testoria CLI

## Overview

`testoria` is a command-line client that pushes automated test results into
Testoria from a CI pipeline in one command. It lives in `cli/` in this repo (its
own package, `testoria-cli`) so the client contract cannot drift from the API —
one PR changes both sides, and `ci.yml` checks it on every backend change.

It talks HTTP like any other client and must never import from `app/`.

## Commands

| Command | Purpose |
|---------|---------|
| `testoria upload <report>` | Upload JUnit XML or JSON results into a run |
| `testoria whoami` | Show what the current credentials are actually allowed to do |
| `testoria auth login \| status \| logout` | Interactive login for humans |
| `testoria run create \| list \| show \| close` | Manage test runs |
| `testoria case list --unmapped` | Find cases with no `automation_id` |

Every command takes `--output json`.

## The CI hot path

```bash
export TESTORIA_URL=https://api.testoria.example
export TESTORIA_API_KEY=tsk_a1b2c3d4_…

testoria upload reports/junit/api.xml --run 42
testoria upload reports/junit/api.xml --project 7 \
    --create-run "CI #$BUILD" --close-on-finish
```

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Uploaded |
| `1` | Transport, auth, or usage error |
| `2` | Unmatched test cases — **only** with `--strict` |

`2` is what a pipeline gates on to catch a test rename that silently stopped
reporting. It belongs on a dedicated drift-check job rather than the regression
job: an uncatalogued test is a cataloguing problem, and failing the nightly on it
trains people to ignore the signal.

## Authentication

API key (`X-API-Key`) for CI, JWT for humans — see
`docs/02-architecture/backend/auth.md`. The key is resolved from `--api-key` or
`TESTORIA_API_KEY` only and is **never written to disk**; only JWTs reach
`~/.testoria/config.yaml` (mode `0600`). Resolution order is flag > env > file,
and exactly one credential is ever sent (the server rejects both at once).

## Constraints

- Matching and parsing are server-side. The CLI deliberately does not
  re-implement them — two implementations of the same rules is how a client
  drifts from its API. Local parsing exists only to fail fast on a file that is
  not a report.
- Re-running an upload is safe: results upsert on `(run, case)` and a no-op
  resubmit writes no history. The upload `POST` is not auto-retried.
- `--attach` matches a file's **stem** to a case's `automation_id`; files that
  match nothing are reported, never silently dropped.
- No pytest plugin — pytest already emits JUnit XML with `--junitxml`.
